# zel-analysis Action / Artifact / Runfiles model (for the Execution agent)

Status: **stable additive layer, v1**. Nothing existing was removed: `ActionAnalysisMetadata`
(flat 4-variant enum) still works and is what `zel-exec` consumes today.

## Artifact (`zel_analysis::Artifact`)
Fields: `is_source`, `is_tree_artifact`, `root: ArtifactRoot {Source,Bin,Genfiles}`,
`is_unresolved_symlink`, `exec_path` (`bazel-out/<cfg>/bin/<pkg>/x`, or source path),
`root_relative_path`, `owner_label`. Constructors: `Artifact::source`, `Artifact::derived`
(Bin), `Artifact::derived_in_root`. Accessors mirror `File`: `basename()`, `extension()`,
`dirname()`, `short_path()` (`../repo/x` for external repos), `root_path()`.
Always build with constructors (new fields may be added).

## Action (`zel_analysis::Action`) — preferred typed model
Common fields: `owner`, `owner_kind`, `owner_config`, `mnemonic`, `progress_message`,
`env`, `execution_requirements`, `inputs` (superset incl. tools), `tools`, `outputs`,
`resource_set` (`memory_mb`, `cpu`, `local_test_count`), `use_default_shell_env`,
`exec_group`, `input_manifests` (runfiles manifests an executable tool needs), `kind`.

`ActionKind`:
* `Spawn { executable, arguments: Vec<CommandLineArgs>, shell_command }` – `ctx.actions.run/run_shell`.
  Each `CommandLineArgs` has the expanded `args` and optional `ParamFileInfo`.
  `Action::command_line()` returns `(argv, param_files)` where param files
  (`(exec_path, bytes)`) **must be written before the spawn runs**; a param file is used when
  `use_always` or the args exceed `DEFAULT_PARAM_FILE_THRESHOLD`.
* `FileWrite { content: FileContent, is_executable }` – `Action.outputs[0]` is the file.
* `Symlink { target_file | target_path, is_executable }` – `target_path` ⇒ unresolved symlink.
* `TemplateExpand { template, substitutions, computed_substitutions, is_executable }`.

`Action::lower() -> Vec<ActionAnalysisMetadata>` converts to the flat model (param files
become preceding `FileWriteAction`s and extra spawn inputs). **Until you migrate, keep consuming
`ActionAnalysisMetadata`; nothing else is required.** `Action::key()` is the action key;
`Action::can_be_shared` implements `Actions.canBeShared`.

## ActionGraph
`ActionGraph::register(&Action) -> Result<(), ActionConflict>`: same-output conflict with
Bazel's `file '…' is generated by these conflicting actions:` text and prefix-conflict text;
identical shareable actions are accepted.

## Runfiles
`Runfiles { artifacts, symlinks, root_symlinks, empty_filenames, suppress_init }` with
`merge`, `manifest_entries(workspace)` and `manifest_text(workspace)`.
`RunfilesSupport { runfiles, executable, runfiles_dir (<exe>.runfiles), manifest, workspace_name }`
with `inputs()`. The runfiles tree materialisation is the executor's job: create
`<exe>.runfiles/<key>` symlinks to the paths in `manifest_entries` (empty value ⇒ empty file).

## ConfiguredTarget (extended, still `Clone + PartialEq + Eq`)
Legacy fields unchanged (`default_info`, `output_groups`, `actions` = lowered flat actions,
`is_test`). New: `typed_actions: Vec<Action>`, `providers: BTreeMap<key, Value>`
(`DefaultInfo`, `OutputGroupInfo`, Starlark providers keyed `<bzl label>%<Name>`),
`runfiles_support: Option<RunfilesSupport>`, `testonly`, `visibility`.
Always construct with `ConfiguredTarget::new(label, cfg, rule_class)`.

## Producing configured targets (what the server should call)
```rust
let loader = PackageLoader::new(cfg);                  // zel-packages
let analyzer = zel_rules::TargetResolver::new(loader, zel_rules::AnalysisConfig::new());
let ct = analyzer.analyze(&label, &BuildConfigurationKey::target(cpu, mode))?; // Arc<ConfiguredTarget>
```
`analyze` memoizes per (label, configuration), resolves dependencies (also under exec/transitioned
configurations), runs Starlark rule implementations and native rules, performs select()
resolution, visibility/testonly checks, toolchain resolution (`AnalysisConfig::registered_toolchains`,
`extra_execution_platforms`) and cycle detection. **It returns `Err(String)` with Bazel's error text on
analysis failure; callers must report it** (the old `if let Ok(ct) = analyze_target(..)` pattern in
`zel-server` silently drops analysis errors). `zel_rules::analyze_target(target, cfg)` still exists for
leaf rules without dependencies.

Artifacts: output dir is `bazel-out/<cfg.mnemonic()>/bin/...` (`darwin_arm64-fastbuild`,
`k8-opt-exec`, `k8-fastbuild-ST-<hash>` after a transition). Genfiles are merged into `bin`.

Runfiles manifests: for every executable/test rule a `SourceSymlinkManifest` FileWrite action writes
`<exe>.runfiles_manifest` (`<runfiles path> <exec-root-relative source path>` lines; Bazel writes
absolute paths — the executor should create `<exe>.runfiles/` symlinks from
`RunfilesSupport.runfiles.manifest_entries(workspace)` rather than trusting the text).

Rule classes with no implementation (`cc_*`, `java_*`, `py_*`, `proto_library`, ...) return an
analysis error; there are no placeholder outputs any more.

## Wave 2 additions (analysis engine wired into the server)

### Server wiring (`zel-server/src/analysis_phase.rs`)
* `build_config_key` builds the top-level `BuildConfigurationKey` from the command line:
  `--cpu`, `--compilation_mode`, `--define`, `--platforms` (labels canonicalised through the main
  repository's Bzlmod mapping), user build settings `--//pkg:flag=v`, and a whitelist of native
  options (`copt`, `cxxopt`, `features`, `stamp`, `collect_code_coverage`, `host_platform`,
  `extra_toolchains`, ...) in `options`.
* `analysis_config` builds `AnalysisConfig`: `--extra_toolchains` then the module graph's
  `register_toolchains` (`zel_bzlmod::resolver::installed_registrations()`), `--extra_execution_platforms`
  then `register_execution_platforms`, `--host_platform`, the canonical name of `@platforms`,
  `--check_visibility`. Patterns are expanded lazily on the first toolchain resolution
  (`PatternExpander`), so unused registrations that cannot load never fail a build.
* `analyze_roots` runs `TargetResolver::analyze_with_aspects` for every requested target, expands
  `test_suite`s, applies `--aspects`/`--aspects_parameters`, checks for action conflicts
  (`TargetResolver::action_graph`), and prunes the actions to the ones the requested outputs need
  (`select_actions`: default group / `--output_groups` / `_validation` / runfiles). Errors are printed as
  `ERROR: <loc>: in <rule> rule //x: ...`, `ERROR: Analysis of target '//x' failed; build aborted: Analysis of target '//x' failed`,
  `ERROR: Build did NOT complete successfully` (exit 1); with `--keep_going` the target is skipped
  with `WARNING: errors encountered while analyzing target '//x', it will not be built.`.
* `zel_skyframe::ConfiguredTargetFunction::with_analysis` runs the same dependency-aware analysis.

### Output directory names
`BuildConfigurationKey::mnemonic()` is `<cpu>-<compilation_mode>[-<platform_suffix>][-ST-<hash>]`.
`cpu`, `compilation_mode` and `platform_suffix` are explicit in the name and never hashed. The hash is
Bazel's `OutputPathMnemonicComputer.transitionDirectoryNameFragment`: SHA-256 of the protobuf
varint-length-prefixed `"<option>=<java toString of value>"` strings of the options that differ from the
baseline (top-level) configuration, sorted by key, first 12 hex digits. The exec configuration is
`<cpu>-opt-exec-ST-d57f47055a04` (platforms = `[@@platforms//host:host]` vs `[]`), verified against
a real Bazel output directory name. `BuildConfigurationKey::to_exec_for(platform)` is the exec transition.

### Aspects
`aspect()` (zel-packages `aspect.rs`) → `Value::Host("aspect", n)`. `apply_aspect` (zel-analysis
`starlark_rule_aspect.rs`) implements `attr_aspects` propagation, `required_providers`, `requires`,
aspect attrs/parameters, `ctx.rule.{kind,attr,file,files,executable}`, `ctx.aspect_ids`, aspect
toolchains, `provides` checks, output-group merging and provider conflict errors. Memoised in
`DepResolver::aspect_cache_*`.

### Other API surface
split transitions + `ctx.split_attr`, `analysis_test_transition`, `rule(analysis_test = True)`
(`AnalysisTestResultInfo` → executable script), `config.exec(exec_group = ...)`, exec groups with their own
toolchain contexts (`ctx.exec_groups[g].toolchains[t]`), `subrule`, `attr.int_list`,
`attr.string_keyed_label_dict`, late-bound defaults (`configuration_field`), `ctx.fragments`
(cpp/platform/java/py/proto/coverage contents), `RunEnvironmentInfo` → `ConfiguredTarget::run_environment`,
`coverage_common.instrumented_files_info` → `ConfiguredTarget::instrumented_files`,
`ctx.target_platform_has_constraint`, `config_common.toolchain_type` at analysis time.

### Tree artifacts in `Args`
`args.add_all([tree_artifact])` (no `map_each`) emits `zel_analysis::TREE_MARKER` placeholders;
`expand_tree_artifact_args(argv, list_dir)` expands them at execution (called from `zel-exec`).

### Dumping the action graph
`TargetResolver::action_graph(extra)` returns the global `ActionGraph` (all typed actions, conflict
checked); `ActionGraph::actions()` iterates them. `Action::command_line()`, `inputs`, `outputs`, `env`,
`execution_requirements`, `exec_group` hold everything aquery needs.
